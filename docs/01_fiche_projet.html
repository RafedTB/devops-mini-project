Étape 1 : Fiche Projet & Analyse des Risques

Atelier Test et Validation des Logiciels • Licence 3 Technologies de l'Information

Cadrage Méthodologique & Objectifs du Livrable
Le projet NestLearn (plateforme e-commerce et gestion d'avis clients) constitue le socle applicatif de la démarche. Ce livrable définit le périmètre d'homologation (authentification JWT, catalogue produits, avis et notations de 1 à 5 étoiles) ainsi que l'analyse préventive des risques qualité majeurs selon les normes ISTQB.

1. Architecture de l'Application Testée

1. Frontend (Interface)

Site Web en React où l'utilisateur se connecte, regarde le catalogue et laisse un avis.

2. Backend (API)

Serveur en NestJS qui applique les règles de sécurité et les calculs.

3. Base de données

Base PostgreSQL qui stocke les utilisateurs, les produits et les avis.

2. Règles Métier de Référence

  • Comptes : Un email doit être unique et valide. Mot de passe $\ge 6$ caractères. Deux rôles : user (client) et admin.
  • Produits : Seul un admin peut créer ou supprimer un produit. Le prix doit être positif ($\ge 0$).
  • Avis & Notes : La note doit être comprise entre 1 et 5 étoiles. Un utilisateur ne peut modifier que ses propres avis.
  • Sécurité : Un simple utilisateur ne doit JAMAIS pouvoir accéder aux routes de l'administrateur.

3. Périmètre des Tests (In-Scope vs Out-Scope)

Périmètre Inclus (In-Scope)

  • La connexion / déconnexion (login)
  • Les droits d'accès (user vs admin)
  • L'ajout de produit et le dépôt d'avis
  • Les erreurs quand on envoie des mauvaises données
  • La sauvegarde en base de données

Périmètre Exclu (Out-Scope)

  • Les vrais paiements bancaires (pas de vraie carte)
  • L'envoi réel de milliers d'emails sur internet
  • Les vieux navigateurs d'il y a 15 ans
  • Les attaques de hackers de haut niveau

4. Définitions Clés ISTQB

1. Erreur

La faute commise par le développeur (ex : il oublie de vérifier la note).

2. Défaut (Bug)

Le problème dans le code (ex : le code accepte une note de 10 étoiles).

3. Défaillance

Ce que l'utilisateur voit (ex : le site plante ou affiche une fausse moyenne).

4. Vérification vs Validation

Vérification : « Le code respecte-t-il la consigne ? »
Validation : « Le logiciel sert-il vraiment à l'utilisateur ? »

5. Matrice des Risques Qualité Majeurs

Risque / Bug possible Pourquoi c'est grave ? Criticité Comment on le teste ?
Piratage de rôle (Bypass) Un simple client devient admin ou supprime les avis des autres. Élevé Tester l'API avec un faux compte pour vérifier qu'on reçoit une erreur 403 (Interdit).
Note invalide (ex: -1 ou 10) Fausse toutes les moyennes d'avis sur les produits. Élevé Tester avec 0, 6, et des textes pour voir si le backend refuse.
Prix négatif (ex: -20€) L'utilisateur achète gratuitement ou gagne de l'argent. Moyen Tester l'envoi d'un prix de -10€ pour vérifier le rejet.
Suppression orpheline Si on supprime un produit, les avis restent seuls et font crasher l'appli. Moyen Vérifier en base de données les relations de clés étrangères.
