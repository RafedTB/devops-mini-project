Étape 5 : Transitions d'État & Tests Exploratoires

Atelier Test et Validation des Logiciels • Licence 3 Technologies de l'Information

Cadrage Méthodologique & Objectifs du Livrable
Cartographie du cycle de vie des commandes via un modèle à états finis, identification des transitions autorisées et interdites, et restitution d'une session de test exploratoire documentant les premières anomalies constatées.

1. Cycle de Vie et Diagramme de Transitions d'État

Chaque commande traverse une séquence logique d'états :

1. CRÉÉE (Panier)
→
2. PAYÉE
→
3. EXPÉDIÉE
→
4. LIVRÉE (Clôturée)
Transition alternative : CRÉÉE ou PAYÉE → ANNULÉE

2. Matrice des Transitions Autorisées et Interdites

Tester les transitions interdites permet de détecter des failles de logique métier :

État Initial Événement / Action État Cible Validité Règle Métier & Comportement Attendu
CRÉÉE Paiement validé PAYÉE Autorisée Transition normale : la commande passe au statut payé (200 OK).
PAYÉE Colis remis au transporteur EXPÉDIÉE Autorisée L'administrateur renseigne le numéro de suivi postal.
EXPÉDIÉE Confirmation de réception LIVRÉE Autorisée Clôture du cycle de commande.
CRÉÉE Passage direct à LIVRÉE LIVRÉE Interdite Bug critique : Impossible de livrer sans paiement préalable. Rejet 400.
LIVRÉE Demande d'annulation ANNULÉE Interdite Une commande déjà livrée ne peut plus être annulée (il faut passer par les retours).
ANNULÉE Paiement tardif PAYÉE Interdite Une commande annulée est définitivement fermée.

3. Charte et Démarche de Test Exploratoire

Au lieu de suivre des scénarios rigides, le testeur adopte l'attitude d'un utilisateur réel pour stresser le système.

Charte 1 : Le Double-Clic Frénétique

Cliquer 4 fois très rapidement sur le bouton « Confirmer la commande ».
Résultat attendu : 1 seule commande créée, le bouton se désactive pour éviter le double débit.

Charte 2 : Le Rafraîchissement brutal (F5)

Appuyer sur F5 en plein milieu de la validation du panier.
Résultat attendu : Le panier n'est pas perdu, aucune commande fantôme créée.

Charte 3 : Injection de caractères spéciaux

Taper des balises HTML comme <script>alert(1)</script> dans un commentaire d'avis.
Résultat attendu : Texte affiché tel quel sans exécution (protection XSS).

4. Fiches d'Anomalie Détectées (Bug Reports)

Exemples de rapports de bugs formalisés selon le standard professionnel :

[BUG-01] Double soumission possible lors de la création d'un avis Sévérité : Moyenne

Module : Avis Produits (Frontend + Backend)

Étapes pour reproduire :
1. Se connecter avec le compte client1@nestlearn.com.
2. Ouvrir le produit ID 2 (Clavier).
3. Remplir le commentaire et cliquer 3 fois très vite sur « Envoyer ».
Résultat observé : 2 avis identiques créés avec 1 seconde d'écart.
Résultat attendu : Le bouton doit se désactiver instantanément après le 1er clic (état loading).

[BUG-02] Erreur 500 au lieu de 400 si un prix est envoyé sous forme de texte Sévérité : Élevée

Module : API Backend (POST /products)

Étapes pour reproduire :
1. Envoyer une requête POST avec le body { "price": "cent_euros" }.
Résultat observé : Le serveur renvoie un code HTTP 500 Internal Server Error avec un crash TypeORM.
Résultat attendu : Le serveur doit intercepter l'erreur avec class-validator et renvoyer un code HTTP 400 Bad Request propre.
