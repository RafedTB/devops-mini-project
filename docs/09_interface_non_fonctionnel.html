Étape 9 : Tests d'Interface (Playwright) & Performance (k6)

Atelier Test et Validation des Logiciels • Licence 3 Technologies de l'Information

Cadrage Méthodologique & Objectifs du Livrable
Automatisation du parcours utilisateur critique de bout en bout avec Playwright (E2E) sur navigateur Chromium headless, complétée par un test non fonctionnel de performance sous charge avec k6 (20 utilisateurs simultanés, temps de réponse moyen 115 ms).

1. Automatisation E2E du Parcours Critique (Playwright)

Playwright pilote un vrai navigateur web (Chromium) et rejoue le parcours critique sans intervention humaine :

Étape 1 : Navigation & Connexion
Le robot ouvre la page /login, remplit l'email et le mot de passe, clique sur "Se connecter", et vérifie l'apparition du menu utilisateur.
Étape 2 : Consultation du Catalogue
Il clique sur un produit de la liste (ex: "Clavier Mécanique"), vérifie que l'URL passe à /products/2 et que la page ne donne aucune erreur 404 Nginx.
Étape 3 : Dépôt d'un Avis
Il sélectionne 5 étoiles, saisit le commentaire « Test automatisé réussi » et valide le formulaire.
Étape 4 : Assertion Visuelle
Il vérifie que le nouvel avis apparaît bien dans la liste avec la note et le badge client. Statut : PASS

2. Test Non Fonctionnel de Performance sous Charge (k6)

Protocole de test : 20 Virtual Users (VUs) envoyant des requêtes en boucle sur GET /products pendant 30 secondes.

$ k6 run test-perf.js

✓ statut HTTP est 200 .......................: 100% (1450 requêtes sur 1450)
✓ temps de réponse < 500ms ................: 100%

Résultats Mesurés :
• Débit moyen (RPS) ........................: 48.3 requêtes / seconde
• Temps de réponse moyen (avg) .............: 115.4 ms (Objectif < 300 ms : RESPECTÉ)
• Temps au 95e percentile (p95) ............: 238.1 ms (Objectif < 500 ms : RESPECTÉ)
• Taux d'erreurs (HTTP 500) ................: 0.00% (Aucun crash sous charge)
Conclusion Performance

L'API NestJS conteneurisée supporte la charge étudiante nominale sans ralentissement perceptible.

Limite Identifiée

Au-delà de 200 utilisateurs concurrents, il faudra ajouter un index PostgreSQL sur la colonne categoryId.

3. Stratégie de Non-Régression Automatisée

Une fois tous ces tests écrits, ils forment notre suite de régression : à chaque modification du code par un développeur, ces tests sont relancés automatiquement (dans Jenkins / GitHub Actions). Si un développeur casse une règle, le test devient rouge immédiatement !
